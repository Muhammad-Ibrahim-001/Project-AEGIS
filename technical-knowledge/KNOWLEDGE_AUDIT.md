## 1. Executive Summary & Audit Verdict

### 1.1 Overall Assessment of the Knowledge Base
The initial knowledge base established a comprehensive structural foundation mapping the 11-stage DWBI course architecture to a modern Databricks Serverless Cloud Lakehouse. However, an independent technical audit identified **8 significant technical discrepancies, outdated assumptions, and missing platform nuances**:

1. **DataFrame Caching on Serverless Compute (Outdated Claim):** The previous claim that all caching (`.cache()`, `.persist()`) is prohibited on Serverless Compute was based on deprecated early serverless limitations. Official Databricks documentation confirms that `df.cache()` and `df.persist()` are fully supported in **Serverless Environment Version 5+**, materializing session-local disk snapshots (`DISK_ONLY`), whereas only SQL `CACHE TABLE` and `spark.catalog.cacheTable()` throw exceptions.
2. **Identity Columns in Delta `MERGE INTO` (Nuance Correction):** The claim that `WHEN NOT MATCHED THEN INSERT *` unconditionally fails was overly broad. `INSERT *` works if the source dataset does not contain an identity column; failure occurs specifically when `UPDATE SET *` attempts to overwrite an identity column, or when source data supplies values to a `GENERATED ALWAYS` column. Furthermore, `GENERATED ALWAYS` strictly prevents seeding default surrogate keys (`-1 = Unknown`), requiring `GENERATED BY DEFAULT AS IDENTITY`.
3. **Missing Foreign Key DDL in Repository (Code vs. Doc Discrepancy):** Knowledge base documents cited `warehouse.sql#L30-L86` as implementing Primary and Foreign Key constraints. Inspection of `warehouse.sql` proves that **zero Foreign Key constraints** and zero fact table Primary Key constraints are implemented; only dimension primary keys exist.
4. **Data Type Mismatches in Diagrams (Mermaid vs. SQL):** `01_Project_Documentation/schema_diagram_mermaid.md` declares surrogate keys as `int`, which directly contradicts Delta Lake identity column requirements (`BIGINT` only). Additionally, the diagram labels fact tables as "Partitioned" rather than "Liquid Clustered" and references legacy PostgreSQL schema names.
5. **Excel Extraction Constraints on Serverless Compute:** Databricks Serverless Compute does not support raw Maven coordinates, making cluster-level installation of `com.crealytics:spark-excel` impossible. Excel extraction for EIA-860/923 must be executed via driver-side Python libraries (`pandas` / `openpyxl`) from `/Volumes/...` or pre-converted.
6. **Enforced vs. Informational Constraints Clarification:** While Unity Catalog `PRIMARY KEY` and `FOREIGN KEY` constraints are informational only, `NOT NULL` constraints (present in `config.py`) are **actively enforced** by Delta Lake (upgrading table protocol to writer version 3) and will abort transactions on null insertion.
7. **ANSI SQL Mode & Sentinel Casting Failures:** Modern Databricks SQL and DBR 14.0+ enable ANSI mode by default. Standard `CAST()` on federal sentinel strings (`"."`, `"NM"`) will abort transactions with `CAST_INVALID_INPUT`. Pipelines must defensively employ `TRY_CAST()`.
8. **Timestamp Literal Syntax in DDL:** `warehouse.sql#L71` specifies `valid_to TIMESTAMP DEFAULT TIMESTAMP('9999-12-31 23:59:59')`. In ANSI mode, Databricks SQL requires the literal syntax `TIMESTAMP '9999-12-31 23:59:59'` without function parentheses.

## 3. Detailed Audit Findings & Corrective Action Matrix

### Finding 1: DataFrame Caching on Databricks Serverless Compute
* **Classification:** [DOC-VERIFIED]
* **Original Claim in Knowledge Base:**  
  *In `ENVIRONMENT.md` and `COMPATIBILITY_BASELINE.md`:*  
  *"No DataFrame/SQL Caching: Explicit manual caching commands—such as `.cache()`, `.persist()`, or `CACHE TABLE`—are not supported and will throw an exception if invoked."*
* **Audit Result:** **INCORRECT / OUTDATED.**
* **Evidence & Official Source:**  
  Official Databricks Documentation: *Serverless compute limitations & DataFrame caching* ([Databricks Serverless Documentation](https://docs.databricks.com/compute/serverless/limitations.html)).  
  Starting in **Serverless Environment Version 5+** (and Databricks Connect for Python 18.1.8+), Databricks added native support for `df.cache()`, `df.persist()`, and `df.unpersist()`. On Serverless Compute, cached DataFrames are materialized eagerly as session-local disk/volume snapshots (`DISK_ONLY`).
* **Applicable Version / Environment:** Databricks Serverless Compute (Environment v5+).
* **Corrected Understanding:**  
  * `df.cache()` and `df.persist()` **are supported** on modern serverless compute; they evaluate eagerly and store session-private snapshots in cloud storage.
  * SQL `CACHE TABLE` / `UNCACHE TABLE`, `spark.catalog.cacheTable()`, and `df.checkpoint()` **remain unsupported** and throw runtime exceptions.
* **Required Action:** Update `ENVIRONMENT.md` and `COMPATIBILITY_BASELINE.md` to reflect accurate Serverless Environment v5+ caching behavior.

### Finding 2: Identity Columns, `MERGE INTO`, and Default Surrogate Keys
* **Classification:** [DOC-VERIFIED] & [REPO-VERIFIED]
* **Original Claim in Knowledge Base:**  
  *In `COMPATIBILITY_BASELINE.md` section 2.3:*  
  *"Attempting to execute `MERGE INTO ... WHEN NOT MATCHED THEN INSERT *` will throw runtime exception `DELTA_IDENTITY_COLUMNS_EXPLICIT_INSERT_NOT_SUPPORTED`. With `GENERATED ALWAYS`, the database prohibits any explicit value assignment."*
* **Audit Result:** **PARTIALLY IMPRECISE & INCOMPLETE.**
* **Evidence & Official Source:**  
  Official Databricks Documentation: *Use identity columns in Delta Lake* ([Databricks Delta Docs](https://docs.databricks.com/delta/identity-columns.html)).
  * In Delta Lake, `WHEN NOT MATCHED THEN INSERT *` **automatically handles** the identity column by generating the next sequence number, provided the source DataFrame does NOT contain an identity column.
  * The error occurs when:
    1. `WHEN MATCHED THEN UPDATE SET *` is used, because Delta attempts to update all columns including the immutable identity column (resolved via `UPDATE SET * EXCEPT (generator_key)` or explicit column assignments).
    2. The source dataset schema includes the identity column and tries to pass values into a `GENERATED ALWAYS` column.
    3. The application attempts to insert a default dimensional row with surrogate key `-1` (e.g., `-1 = Not Applicable` for non-thermal plants). `GENERATED ALWAYS` strictly forbids manual key overrides.
* **Applicable Version / Environment:** Delta Lake 2.2+, Databricks Runtime 10.4 LTS+, Databricks Serverless.
* **Corrected Understanding:**  
  Tables intended to hold standard Kimball default surrogate keys (`-1`) cannot use `GENERATED ALWAYS AS IDENTITY`. They must use `GENERATED BY DEFAULT AS IDENTITY`. For SCD Type 2 merges on `dim_generator`, `UPDATE SET *` must exclude `generator_key`.
* **Required Action:** Update `COMPATIBILITY_BASELINE.md` to document the precise conditions under which `MERGE INTO` succeeds or fails, and recommend `GENERATED BY DEFAULT AS IDENTITY` for dimensional tables.

### Finding 5: Excel Ingestion Mechanism on Databricks Serverless Compute
* **Classification:** [DOC-VERIFIED]
* **Original Claim in Knowledge Base:**  
  *In `PROJECT_PROFILE.md` and `DEPENDENCY_MAP.md`:*  
  *"PySpark Bronze Extractors read multi-tab Excel files directly from Volume landing."*

Ingestion must use Python `pandas` / `openpyxl` on the driver node to parse the file from the POSIX Volume mount (`/Volumes/...`), followed by `spark.createDataFrame(pdf)` to load into Bronze Delta tables, or pre-converted to CSV/Parquet prior to upload.
* **Required Action:** Detail this driver-memory bottleneck and architectural requirement in `COMPATIBILITY_BASELINE.md` and `ENVIRONMENT.md`.

### Finding 6: Enforced vs. Informational Constraints in Delta Lake
* **Classification:** [DOC-VERIFIED] & [REPO-VERIFIED]
* **Original Claim in Knowledge Base:**  
  *In `COMPATIBILITY_BASELINE.md` section 2.5:*  
  *"Constraints in Databricks: Informational only and not enforced."*
* **Audit Result:** **OVERLY GENERALIZED / MISLEADING.**
* **Evidence & Official Source:**  
  Official Databricks Documentation: *Constraints on Databricks* ([Databricks Constraints Docs](https://docs.databricks.com/tables/constraints.html)).
  * Delta Lake categorizes constraints into two distinct groups:
    1. **Informational Constraints:** `PRIMARY KEY` and `FOREIGN KEY` (available in Unity Catalog). They are NOT enforced upon insertion.
    2. **Enforced Constraints:** `NOT NULL` and `CHECK` constraints. They ARE actively enforced by Delta Lake on every write operation (`INSERT`, `UPDATE`, `MERGE`).
  * In `03_ETL/config.py#L326-L352`: `batch_id STRING NOT NULL`, `rejection_reason STRING NOT NULL`, `raw_payload_json STRING NOT NULL`.
* **Applicable Version / Environment:** Delta Lake (Protocol Version 3+), Databricks Runtime, Databricks Serverless.
* **Corrected Understanding:**  
  If any ingestion or quarantine query passes a null value into a column declared `NOT NULL`, Delta Lake will immediately abort the transaction. Unenforceability applies strictly to Primary and Foreign Keys.
* **Required Action:** Update `COMPATIBILITY_BASELINE.md` to clearly delineate enforced constraints (`NOT NULL`, `CHECK`) from informational constraints (`PRIMARY KEY`, `FOREIGN KEY`).

### Finding 7: ANSI SQL Mode & Sentinel Value Casting in Databricks SQL
* **Classification:** [DOC-VERIFIED] & [REPO-VERIFIED]
* **Original Claim in Knowledge Base:**  
  *In `COMPATIBILITY_BASELINE.md`:*  
  *"Data type coercion must replace `.` and `NM` with SQL NULL... Handled via CAST."*
* **Audit Result:** **POTENTIAL RUNTIME FAILURE UNDER ANSI MODE.**
* **Evidence & Official Source:**  
  Official Databricks Documentation: *ANSI compliance in Databricks Runtime* ([Databricks ANSI Docs](https://docs.databricks.com/sql/language-manual/sql-ref-ansi-compliance.html)).
  * In Databricks SQL and Databricks Runtime 14.0+, **ANSI SQL mode is enabled by default** (`spark.sql.ansi.enabled = true`).
  * Under ANSI mode, executing `CAST('.' AS DOUBLE)` or `CAST('NM' AS INT)` does NOT return `NULL`; it throws a fatal runtime exception: `CAST_INVALID_INPUT`.
  * To safely coerce sentinels to `NULL` without crashing pipelines, Databricks SQL provides `TRY_CAST()`.
* **Applicable Version / Environment:** Databricks SQL Serverless, Databricks Runtime 14.0+.
* **Corrected Understanding:**  
  Any Bronze-to-Silver transformation script using standard `CAST()` on raw columns containing un-sanitized string sentinels will fail. Silver pipelines must use `TRY_CAST(column AS numeric_type)`.
* **Required Action:** Add `TRY_CAST` as a mandatory compatibility standard in `COMPATIBILITY_BASELINE.md` and `IMPLEMENTED_TECHNOLOGIES.md`.

### Finding 8: ANSI Timestamp Literal Syntax in Delta DDL
* **Classification:** [DOC-VERIFIED] & [REPO-VERIFIED]
* **Original Claim in Knowledge Base:**  
  *In `IMPLEMENTED_TECHNOLOGIES.md`:*  
  *"`valid_to TIMESTAMP DEFAULT TIMESTAMP('9999-12-31 23:59:59')` is valid DDL."*
* **Audit Result:** **SYNTACTIC AMBIGUITY / ANSI CONFLICT.**
* **Evidence & Official Source:**  
  Official Databricks SQL Language Reference: *Timestamp literals* ([Databricks Timestamp Literals](https://docs.databricks.com/sql/language-manual/data-types/timestamp-type.html)).
  * Standard Databricks SQL / ANSI literal syntax for timestamp defaults is:
    `valid_to TIMESTAMP DEFAULT TIMESTAMP '9999-12-31 23:59:59'` (without parentheses).
  * Using `TIMESTAMP('...')` with parentheses is parsed as a function call, which may be rejected or trigger deprecation warnings in strict ANSI DDL parsers.
* **Applicable Version / Environment:** Databricks SQL DDL, Databricks Runtime 14.1+.
* **Corrected Understanding:**  
  The DDL drafted in `archived/early_sql_drafts/warehouse.sql#L71` should use the ANSI standard literal format `TIMESTAMP '9999-12-31 23:59:59'`.
* **Required Action:** Record this correction in `COMPATIBILITY_BASELINE.md` and `IMPLEMENTED_TECHNOLOGIES.md`.
